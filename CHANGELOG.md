## [Unreleased]

### Added
- M2 — parallel downloads (#4), in progress:
  - `zajil-platform`: `write_at` (every connection writes through the one locked handle), `available_space`, and `allocate`: real reservation on Linux (`fallocate`) and macOS (`F_PREALLOCATE`) where the file system supports it, and a sparse file on Windows (owner decision: no zero-filling of the gap before each far write). Absurd sizes are refused without a panic.
  - Downloads over up to 32 connections (default 8, `zajil get --connections <1..32>`), when the server announces `Accept-Ranges: bytes`, the size and a strong validator; otherwise one connection. The file is split into equal segments of at least 1 MiB; the first response is used for the first segment, every other connection asks for exactly its range with `If-Range`, and only a `206` with exactly that `Content-Range` of the same file is written. A changed file starts over from the new version (never mixed); a server that announces ranges but ignores them is read to the end on the first connection. Tested: 50 MB with 8 and with 32 connections (SHA-256 matches, ranges cover the file exactly), a cut multi-segment download resumes asking for exactly the missing bytes, a `zajil` process killed in the middle of 8 segments resumes from its state file without asking again for counted bytes, a server without ranges gets one request, kept-alive connections are reused (8 ranges on 2 connections), and a benchmark: with each connection limited to 2 MiB/s, 8 connections finish an 8 MiB file more than 3 times faster than one.
  - Credentials in the URL (`user:pass@`) go with every range request and every restart within the same download to the same origin (never to another origin after a redirect), kept in memory only, so a download resumed later from its state file has none; tested with a server that requires `Authorization` on every request, including one that ignores `If-Range` and forces a restart. A file whose validator changes once segments are being asked for (several machines behind one name, each with its own `ETag`) starts over once on a single connection instead of failing; tested. Both found by the review of #24.
  - Dynamic splitting: a connection with no free segment takes the second half of what remains of the segment with the longest time left (remaining bytes ÷ its connection's speed; a connection silent for a second counts as stalled), as long as each half keeps the minimum segment size. Each split is an `Event::Split` and is saved with the next checkpoint. Tested: with one connection limited to 64 KiB/s, a download that would need 32 s for that segment alone ends in about 2.5 s, and the event log shows that segment split first; nothing is split when every connection is fast; a download stopped after a split resumes from its saved segments without starting over.
  - Before any file is created, the size announced by the server must fit in the folder's free space (a huge or false `Content-Length` is refused clearly, tested with 2^60 bytes); the part file then gets its size with `allocate`.
  - State files of several segments: the segments must start at byte 0 and cover the file in order without gaps or overlaps; no check can overflow.
  - Downloads now finish on exFAT under macOS, which refuses both the no-replace rename and hard links (before, every such download stopped at the rename). Only there, the name is checked and a plain rename follows; the small race this leaves is documented in ARCHITECTURE §3.1. CI runs the file helpers and a full download on FAT32 and exFAT images on Windows, macOS and Linux (on Linux, exFAT goes through the FUSE driver when the runner's kernel has no exFAT module, which is what CI runners have had so far; the kernel driver itself is on the manual list). SMB is on the manual list (`docs/MANUAL-TESTS.md`).
- M1 — download engine, single connection and resume (#3). Every item below is covered by an automated test that runs on Windows, macOS and Linux unless it says otherwise:
  - `zajil-platform`: the `AppPaths` interface with Windows, macOS and Linux implementations (each checked on its own system against that system's variables), the ADR-0001 identifiers as constants, and file-system helpers: replace in one step, rename that never overwrites, and open a file only if it is a regular file (no symbolic link, junction or hard link). On Windows, renames request write-through (`MOVEFILE_WRITE_THROUGH`; Microsoft documents a durability guarantee only for moves across volumes) and retry for about a second while antivirus, indexing or OneDrive holds the file (the retry test runs on Windows only); the engine runs these on blocking threads so the wait never stalls the async runtime.
  - File-name sanitization (RFC 6266 §4.3, Windows reserved names and characters, every invisible format character and line/paragraph separator — Unicode Cf, Zl and Zp, each one tested — except ZWNJ and ZWJ where the ContextJ rules of RFC 5892 allow them, never at an edge of the name or next to a dot, and length) and confinement to the download folder, with the same rules on every OS.
  - Per-download state file (`.zajil-state`, schema v1, `docs/STATE-FILE.md`): SHA-256 checksum over a documented canonical form (sorted keys), independent of field order, with a golden v1 file that must always load; strict reading that refuses damaged, oversized or linked files, and atomic writes that never follow a link planted at `.zajil-state.tmp`.
  - `zajil-testserver`: a local HTTP/HTTPS test server for hard cases (no range support, cut connections, changed files, slow and stalled transfers, 429 with `Retry-After`, 403, redirects, dangerous `Content-Disposition` names) with a request log. HTTPS certificates come from a temporary CA created in memory for each test run; no certificate or key is stored in the repository.
  - Single-connection HTTP/HTTPS downloads: the first response is the probe (size, `Accept-Ranges`, `ETag`, `Last-Modified`, name from `Content-Disposition` or the URL); a 50 MB file arrives with a matching SHA-256; IPv6 works on `[::1]`; at most 10 redirects; user names and passwords in a URL are never written to the state file; a file that appears under the same name during the download is not overwritten (the finished file takes a numbered name, shortened first so it never exceeds 200 bytes and can always be resumed); a new download that fails or is cancelled before its first byte leaves no files behind, even when cancelled while its first state save is still running on a blocking thread (tested with a busy blocking pool and with the temporary file held the way an antivirus holds it). Its name stays reserved until that save is over, so a download of the same name started right after the cancellation takes `name (1)` and never loses its data (tested).
  - HTTPS: a download succeeds over TLS 1.3 from a server signed by the test CA, which only tests trust (`test-support` feature, enabled only by dev-dependencies; CI checks the release build lacks it). Self-signed, expired, wrong-host and IP-not-covered certificates are refused before any request; a redirect from https to http is refused; a guard test forbids TLS-bypass APIs in the source.
  - Resume with `Range` and `If-Range` exactly as RFC 9110 §13.1.5 allows: a strong `ETag`, never a weak one, and a `Last-Modified` date only when there is no `ETag` and it is strong (§8.8.2.2: at least one second before the response's `Date`); otherwise the download starts over (tested with a changed file behind a weak `ETag` and behind an unchanged same-second date). HTTP dates outside the years 1900–9999, or on days that do not exist (31 February), are ignored, never compared (tested in debug and release builds, where overflow behaves differently). After a cut at 30 % only the missing bytes are requested; a new `ETag` or a server that answers `200` to `Range` starts over without mixing content; damaged state files are refused before any request; a `.zajil-part` or `.zajil-state` that is a symbolic or hard link is refused, so nothing outside the download folder is written; relative state-file paths work; 64-bit offsets are tested beyond 4 GiB (in `Content-Range` and the state file).
  - The `zajil` command: `zajil get <url> [--dir <folder>]` (defaults to the system Downloads folder) and `zajil resume <state-file>`, with exit codes 0 (done), 1 (failed), 2 (usage) and 3 (stopped but resumable). The printed resume command is quoted for each shell (POSIX shells on macOS and Linux; PowerShell and cmd on Windows) and is run through those shells in a test with a file named `` $(touch PWNED)`id`.zip ``. A process killed mid-download resumes from its state file. Messages are English until translations arrive in M4.

### Not verified yet
- Power loss: interruptions are tested by cutting the connection and killing the process, which keeps the operating system's write cache. A real power cut has not been tested on any system.
- Ctrl+C: it stops the download and prints the resume command, but no automated test covers it; up to one second of data is downloaded again.
- The progress line on the old Windows console (conhost): Zajil enables ANSI mode and otherwise redraws without escape codes; only the fallback is unit-tested.
- A manual run on Windows (planned before the first release); macOS and Linux were run by hand against real servers.
- Disk space: reserved for real on Linux and macOS only where the file system supports it; on Windows the part file is sparse (owner decision, M2), so only the free-space check before the start protects against a full disk.
