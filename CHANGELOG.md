## [Unreleased]

### Added
- M3 — queues, scheduling and speed limits (#5). Every item below is covered by an automated test that runs on Windows, macOS and Linux unless it says otherwise:
  - Retries for the first request and single-connection downloads (owner's decision on #28), with the policy of M2: a request that fails for a reason that may pass (no connection, a broken connection, a timeout, `5xx`, `408`, `429`) is sent again after a growing wait with a random part, and a `429` waits for its `Retry-After` (more than 10 minutes is not waited for: `Error::ServerBusy`). An untrusted certificate, a refused redirect, `403`, `404` and other answers are never retried. A broken single connection first records what is on disk, then asks for the rest with `Range` and `If-Range`; a server that cannot continue from there (no strong validator, ranges ignored, or a changed file) gives the whole file again, written from byte 0 (never mixed). After 5 failures in a row without reaching further into the file the download stops, resumable; `zajil --tries <1..100>` changes the 5 (`Options::max_failures`, also used by segmented downloads), and 1 means no retry. Each retry is an `Event::Retrying`, shown by `zajil`. Tested: the M3 criterion (a server without ranges cuts twice and answers `429` with `Retry-After: 2` once: the download completes, the SHA-256 matches, no request within 2 s of the 429), three server errors on the first request, a cut single connection that continues with a range from where it stopped, a server that always breaks at the same byte (given up after 5 tries, resumable), 503 on every try (5 requests), one try (1 request), a one-hour `Retry-After` (stops at once), `403` and `404` (one request each), and a resume that meets two 503s.
  - `had_credentials` in the state file (schema v1, not published yet; optional, `false` when absent, so the golden file still loads): a `401` while resuming means "a user name and password are needed again" only for a download that had them; otherwise it is a plain `401` (an expired signed link, for example). Tested both ways, reading the written file.
  - The state file can be read by its owner only (owner's decision on #28: a token in the URL such as `?sig=…` stays in it, because resuming needs it): mode `0600` on macOS and Linux (on macOS the access list a file inherits from its folder is removed too, before any byte is written: found by the review of #30, where a folder with `everyone allow read,file_inherit` made a `0600` state file readable by everyone), and on Windows a protected access list with a single entry for the current user, set when the file is created (`zajil_platform::fs::create_private`). Tested on the written file, on Windows also with `icacls`, and on macOS with `ls -le` on a folder given such an access list. Known gap on macOS, documented by the owner's decision on #36 (item 12; `docs/STATE-FILE.md`, writing rule 0): for a moment between creating the temporary file (empty, mode `0600`) and removing the inherited access list, the file has the folder's list, and access is checked only when a file is opened, so another user whom that list lets read, and who opens the file at that very moment (its name is known in advance), could read what is written to it later, the token included. Not fixed yet (a private folder for the temporary file, or `openx_np` with a `filesec`, both need checking). Linux and Windows are not affected.
  - Tokens are never printed: `Error::Http`, `Error::InvalidUrl` and retry messages drop the query, the fragment and any user name and password of the URL. Tested with `?sig=SECRET-TOKEN` against a cut, a stalled, an unreachable and an invalid URL, in the engine's errors and in everything `zajil` prints. Before, an unreachable URL showed its token.
  - Fixed (found by the new cancellation test, behaviour since M1): a new download cancelled while its first state save was still running removed its files when that save ended, even if `zajil resume` had taken them over meanwhile, so the resume failed ("could not give the finished file its name"). The files are now removed only if nobody holds the part file's lock, and the lock is held while they are removed. Tested by cancelling a download that keeps breaking (with and without data) at 9 moments from 0 to 1.2 s, then resuming or downloading again: the right file each time, and nothing else left.
  - Queues (ADR-0007): named queues of downloads, each with its number of downloads at once (default 3, at most 32), kept in `queues.json` in the data folder (`zajil --data-dir` to choose another) with the rules of the state file: a schema version, a SHA-256 checksum, strict reading (links, unknown fields, impossible ids refused; a damaged file is never overwritten), safe writes readable by the user only, and `queues.lock` held by every change from its read to its write, so changes from several processes are never lost (tested with 8 threads adding 120 items at once). `runner.lock` lets one `zajil queue run` run at a time. URLs with a user name or password are not queued (they would have to be saved); a token in a URL is kept but never printed. Commands: `zajil queue add | list | pause | resume | remove | set --max-active | run`; `list` shows each download's progress from its own state file. Tested: the M3 criterion (10 downloads, 2 at once: never more than 2, counted from the runner's events and by the server), two queues of 1 run 2 at once, a failed item does not stop the queue, an item never resumes another download's state file (found by the review of #31: a new download that failed before its first byte kept pointing at its removed state file, whose name another URL then took; resuming it finished the other file and marked it done. Now that pointer is cleared, events of a download that has ended are ignored, and a state file of another URL is never resumed), and the M3 criterion of a `zajil queue run` killed without warning and run again (the setting, the three downloads in order and the progress are kept, the two that had progress resume with ranges only, all three SHA-256 match). Not tested: Ctrl+C on `zajil queue run` (the same stop is tested inside the engine).
  - Stop and wait (#5, deferred from the review of #15): `Stop` with `Engine::download_until` and `resume_until` stops a download, records what is on disk, and returns `Error::Stopped` only once no write or save of it runs and its part file is closed, so it can be resumed at once in the same process. Pausing and removing queue items use it. Tested deterministically with a state save held for 300 ms while the stop is requested (single connection and 4 segments): no save is running when the call returns, the part file is unlocked, and the immediate resume starts from the newest state and ends with the right file; a control test shows that dropping the future instead leaves the save running. A new download stopped before any data leaves no files. Engine event callbacks are now `Send` so downloads can run as tasks.
  - Fixed: a file replaced by a safe save while another process was opening it (a reader of `queues.json` racing a write) was refused as a hard link, because its link count was then 0. Zero links are now allowed; two or more are still refused.
  - Speed limits: one for the whole program (`zajil queue speed-limit <RATE|none>`, kept in the queues file and applied by a running `zajil queue run` within half a second) and one for each download (`zajil get --limit`, `zajil resume --limit`, `zajil queue add --limit`). Rates are bytes per second or K, M, G (KiB/s, MiB/s, GiB/s). A token bucket that every connection goes through, counting each piece as it arrives (bytes then dropped, not written, are given back as credit), with a burst of a tenth of a second; a new rate wakes the connections already waiting (review of #32: a removed limit reached them only minutes later, and counting only after each 256 KiB batch let the first second run 3 to 6 times faster than the limit; both now have tests, the second checking that at no moment more is on disk than the limit allows); two limits are reserved together and waited for once (waiting for one then the other was slower than the lower limit: 0.83 of it, found by a test). Tested on a clock the test owns (owner's decision): 1 MiB/s for the program with two downloads at once (one on four connections), 1 MiB/s for each of two downloads at once, the program's and an item's limit together through the queue runner, all between 0.9 and 1.1 of the limit over at least 6 seconds and stable over repeated runs; plus one test on the real clock (`zajil queue run` with `speed-limit 1M` takes at least 2.6 s for 3 MiB). Bytes a connection reads past the end of its part and drops are not counted, so the wire may carry a little more than the limit; to keep that small, a connection now writes as soon as it passes the end of its part, to learn whether it goes on.
  - Schedules: `zajil queue schedule [--queue NAME] --start HH:MM[:SS] --stop HH:MM[:SS] --days mon,...` (or `--none`) gives a queue a window each day in local time (a stop not after the start ends the next day; without a start, 00:00; without a stop, midnight; without days, every day). Outside its window a queue starts nothing, and its running downloads stop (recording their progress) and resume at the next window; the runner sleeps until the next change and says until when a queue waits. Local time and daylight saving come from the system time zone through `jiff` (Unlicense or MIT). Tested on a frozen clock the test moves (owner's decision): the M3 criterion (scheduled 5 s ahead: nothing at 4 s, started exactly on time), a window closing in the middle of a download that resumes with ranges only at the next day's window, a Saturday-only queue waiting from Friday, an unscheduled queue running while another waits, windows across midnight, days, a start or stop alone, and New York's daylight saving changes; plus the one real-clock test, now with a schedule (it starts within 2 s of its local time, not before).
  - Shut down or sleep after a queue (`PowerControl`, ADR-0006): `zajil queue run --shutdown-after <QUEUE>` or `--sleep-after <QUEUE>` [`--countdown <10..3600 s>`, default 60]. Owner's safety rules: only when asked, for that queue and that run (never saved); only if every download of that queue is done, at least one of them in this run (a queue finished in an earlier run, a failure, a pause or Ctrl+C means no action, and then the run goes on without stopping anything: found by the review of #35); the run then stops the other downloads (which keep their progress) and a clear countdown, cancelled by Ctrl+C, comes first. Implementations: Windows `InitiateShutdownW` (with `SeShutdownPrivilege`) and `SetSuspendState`; macOS the shut-down Apple event `kAEShutDown` (`'shut'`, not `'rsdn'`, which only shows the dialog: found by the review of #35) to `loginwindow` and `pmset sleepnow`; Linux `systemctl poweroff` and `suspend`. Tested with a mock only, on Windows, macOS and Linux: asked exactly once at the end of a 60 s countdown heard second by second on a frozen clock while another queue still had work, never when cancelled, when a download failed or was paused, without the option, after a stopped run or for an empty queue, and a refusal by the system is reported; the CLI shows the countdown and how to cancel it (the test stops it during a one-hour countdown) and keeps the computer on when the queue did not finish. Tests never call the real implementation: a guard test checks that it is named only by the program and that every test starts `zajil` with `ZAJIL_NO_POWER_ACTIONS` set (CI sets it too), with which the real implementation refuses. **The real shutdown and sleep were not run on any system**: manual steps in `docs/MANUAL-TESTS.md`, follow-up in #34 (owner's decision: M3 closes with it pending).
  - CI installs zsh on Linux, and the CLI tests that run printed commands in sh, bash and zsh now fail on CI when a shell is missing instead of skipping it.
  - Owner's decisions on #36: a second test of the speed limit on the real clock (`crates/zajil-core/tests/speed_limit_real_clock.rs`: 1 MiB/s on 8 and 32 connections, at most twice the limit on disk within the first second, the bug of the review of #32 gave 5.5 times; and the average between 0.9 and 1.1 of the limit over the whole 8 MiB, at least 6 s) runs every night on Windows, macOS and Linux (`.github/workflows/nightly.yml`), never on pull requests; a failure opens an issue and does not block a merge. Checked by bringing that bug back: the test failed (2.4 times the limit with 8 connections). It does not cover the line that writes every piece at once under a limit: without that line it still passed. Proxies were moved to M5, import and export of queues to M4, and limits by amount (MB per hour) to after 1.0 (ROADMAP and PARITY).
- M2 — parallel downloads (#4). Every item below is covered by an automated test that runs on Windows, macOS and Linux unless it says otherwise:
  - `zajil-platform`: `write_at` (every connection writes through the one locked handle), `available_space`, and `allocate`: real reservation on Linux (`fallocate`) and macOS (`F_PREALLOCATE`) where the file system supports it, and a sparse file on Windows (owner decision: no zero-filling of the gap before each far write). Absurd sizes are refused without a panic.
  - Downloads over up to 32 connections (default 8, `zajil get --connections <1..32>`), when the server announces `Accept-Ranges: bytes`, the size and a strong validator; otherwise one connection. The file is split into equal segments of at least 1 MiB; the first response is used for the first segment, every other connection asks for exactly its range with `If-Range`, and only a `206` with exactly that `Content-Range` of the same file is written. A changed file starts over from the new version (never mixed); a server that announces ranges but ignores them is read to the end on the first connection. Tested: 50 MB with 8 and with 32 connections (SHA-256 matches, ranges cover the file exactly), a cut multi-segment download resumes asking for exactly the missing bytes, a `zajil` process killed in the middle of 8 segments resumes from its state file without asking again for counted bytes, a server without ranges gets one request, kept-alive connections are reused (8 ranges on 2 connections), and a benchmark: with each connection limited to 2 MiB/s, 8 connections finish an 8 MiB file more than 3 times faster than one.
  - Credentials in the URL (`user:pass@`) go with every range request and every restart within the same download to the same origin (never to another origin after a redirect), kept in memory only, so a download resumed later from its state file has none; tested with a server that requires `Authorization` on every request, including one that ignores `If-Range` and forces a restart. A file whose validator changes once segments are being asked for (several machines behind one name, each with its own `ETag`) starts over once on a single connection instead of failing; tested. Both found by the review of #24.
  - Dynamic splitting: a connection with no free segment takes the second half of what remains of the segment with the longest time left (remaining bytes ÷ its connection's speed; a connection silent for a second counts as stalled), as long as each half keeps the minimum segment size. Each split is an `Event::Split` and is saved with the next checkpoint. Tested: with one connection limited to 64 KiB/s, a download that would need 32 s for that segment alone ends in about 2.5 s, and the event log shows that segment split first; nothing is split when every connection is fast; a download stopped after a split resumes from its saved segments without starting over.
  - Retries and busy servers: a cut, timed-out or `5xx`/`408` connection gives its segment back and it is asked for again, from its first missing byte, after a wait that doubles from 0.5 s up to 30 s with a random part (between half the ceiling and the ceiling); after 5 failures in a row without progress the segment is given up and the download stops, resumable. A `429` stops every new request until its `Retry-After` (seconds or HTTP date; more than 10 minutes is not waited for); a `403` or `429` while other connections work lowers the connection limit to what the server accepted. Reported as `Event::ServerBusy`. Tested: `429` with `Retry-After: 2` (no request within 2 s of any 429, the connections drop to 2 and never rise), `403` beyond 4 connections (completes with 4 or fewer, whole file), 8 cut connections all retried without starting a segment over, 5 tries with growing waits before giving up, and a 1-hour `Retry-After` that stops at once. Not retried in M2: the first request of a download, and single-connection downloads (as in M1); done in M3 (above).
  - Follow-ups decided by the owner on #28: resuming a download that needed a user name and password now fails with a clear `Error::CredentialsNeeded` instead of a bare 401, and `zajil` explains it and how to download the file again: a command that deletes the two old files and the folder for `--dir`, both quoted for each shell because the name comes from the server, then the same `zajil get` (tested by running the printed commands in each shell with a file name and a folder name holding `$(touch PWNED)`, backticks, a space and a quote, then following the steps). The URL and the credentials are never printed. An invalid URL no longer shows its user name or password in the error, even when it lacks `://` or has a mistyped scheme. A test now proves that a file that changes while it is being split ends as the new version in full, without one byte of the old one, although most of the old version was already on disk.
  - Before any file is created, the size announced by the server must fit in the folder's free space (a huge or false `Content-Length` is refused clearly, tested with 2^60 bytes); the part file then gets its size with `allocate`.
  - State files of several segments: the segments must start at byte 0 and cover the file in order without gaps or overlaps; no check can overflow.
  - Downloads now finish on exFAT under macOS, which refuses both the no-replace rename and hard links (before, every such download stopped at the rename). Only there, the name is checked and a plain rename follows; the small race this leaves is documented in ARCHITECTURE §3.1. CI runs the file helpers and a full download on FAT32 and exFAT images on Windows, macOS and Linux (on Linux, exFAT goes through the FUSE driver when the runner's kernel has no exFAT module, which is what CI runners have had so far; the kernel driver itself is on the manual list). SMB is on the manual list (`docs/MANUAL-TESTS.md`).
- M1 — download engine, single connection and resume (#3). Every item below is covered by an automated test that runs on Windows, macOS and Linux unless it says otherwise:
  - `zajil-platform`: the `AppPaths` interface with Windows, macOS and Linux implementations (each checked on its own system against that system's variables), the ADR-0001 identifiers as constants, and file-system helpers: replace in one step, rename that never overwrites, and open a file only if it is a regular file (no symbolic link, junction or hard link). On Windows, renames request write-through (`MOVEFILE_WRITE_THROUGH`; Microsoft documents a durability guarantee only for moves across volumes) and retry for about a second while antivirus, indexing or OneDrive holds the file (the retry test runs on Windows only); the engine runs these on blocking threads so the wait never stalls the async runtime.
  - File-name sanitization (RFC 6266 §4.3, Windows reserved names and characters, every invisible format character and line/paragraph separator — Unicode Cf, Zl and Zp, each one tested — except ZWNJ and ZWJ where the ContextJ rules of RFC 5892 allow them, never at an edge of the name or next to a dot, and length) and confinement to the download folder, with the same rules on every OS.
  - Per-download state file (`.zajil-state`, schema v1, `docs/STATE-FILE.md`): SHA-256 checksum over a documented canonical form (sorted keys), independent of field order, with a golden v1 file that must always load; strict reading that refuses damaged, oversized or linked files, and atomic writes that never follow a link planted at `.zajil-state.tmp`.
  - `zajil-testserver`: a local HTTP/HTTPS test server for hard cases (no range support, cut connections, changed files, slow and stalled transfers, 429 with `Retry-After`, 403, redirects, dangerous `Content-Disposition` names) with a request log. HTTPS certificates come from a temporary CA created in memory for each test run; no certificate or key is stored in the repository.
  - Single-connection HTTP/HTTPS downloads: the first response is the probe (size, `Accept-Ranges`, `ETag`, `Last-Modified`, name from `Content-Disposition` or the URL); a 50 MB file arrives with a matching SHA-256; IPv6 works on `[::1]`; at most 10 redirects; user names and passwords in a URL are never written to the state file; a file that appears under the same name during the download is not overwritten (the finished file takes a numbered name, shortened first so it never exceeds 200 bytes and can always be resumed); a new download that fails or is cancelled before its first byte leaves no files behind, even when cancelled while its first state save is still running on a blocking thread (tested with a busy blocking pool and with the temporary file held the way an antivirus holds it). Its name stays reserved until that save is over, so a download of the same name started right after the cancellation takes `name (1)` and never loses its data (tested).
  - HTTPS: a download succeeds over TLS 1.3 from a server signed by the test CA, which only tests trust (`test-support` feature, enabled only by dev-dependencies; CI checks the release build lacks it). Self-signed, expired, wrong-host and IP-not-covered certificates are refused before any request; a redirect from https to http is refused; a guard test forbids TLS-bypass APIs in the source.
  - Resume with `Range` and `If-Range` exactly as RFC 9110 §13.1.5 allows: a strong `ETag`, never a weak one, and a `Last-Modified` date only when there is no `ETag` and it is strong (§8.8.2.2: at least one second before the response's `Date`); otherwise the download starts over (tested with a changed file behind a weak `ETag` and behind an unchanged same-second date). HTTP dates outside the years 1900–9999, or on days that do not exist (31 February), are ignored, never compared (tested in debug and release builds, where overflow behaves differently). After a cut at 30 % only the missing bytes are requested; a new `ETag` or a server that answers `200` to `Range` starts over without mixing content; damaged state files are refused before any request; a `.zajil-part` or `.zajil-state` that is a symbolic or hard link is refused, so nothing outside the download folder is written; relative state-file paths work; 64-bit offsets are tested beyond 4 GiB (in `Content-Range` and the state file).
  - The `zajil` command: `zajil get <url> [--dir <folder>]` (defaults to the system Downloads folder) and `zajil resume <state-file>`, with exit codes 0 (done), 1 (failed), 2 (usage) and 3 (stopped but resumable). The printed resume command is quoted for each shell (POSIX shells on macOS and Linux; PowerShell and cmd on Windows) and is run through those shells in a test with a file named `` $(touch PWNED)`id`.zip ``. A process killed mid-download resumes from its state file. Messages are English until translations arrive in M4.

### Not verified yet
- M3 shutdown and sleep (`PowerControl`): tested with a mock only; the real calls were never run on any system (#34, `docs/MANUAL-TESTS.md`).
- M3 Ctrl+C on `zajil queue run`: the same stop is tested inside the engine, not through a real Ctrl+C.
- M3 schedules across a real daylight saving change on a machine: tested with time zone rules, not on a live system clock.
- M2 against real servers: every M2 test runs against the local test server. Real CDNs and mirrors that limit connections were not tried yet.
- SMB folders: on the manual list (`docs/MANUAL-TESTS.md`); FAT32 and exFAT are tested on disk images in CI only, not on real USB drives.
- Power loss: interruptions are tested by cutting the connection and killing the process, which keeps the operating system's write cache. A real power cut has not been tested on any system.
- Ctrl+C: it stops the download and prints the resume command, but no automated test covers it; up to one second of data is downloaded again.
- The progress line on the old Windows console (conhost): Zajil enables ANSI mode and otherwise redraws without escape codes; only the fallback is unit-tested.
- A manual run on Windows (planned before the first release); macOS and Linux were run by hand against real servers.
- Disk space: reserved for real on Linux and macOS only where the file system supports it; on Windows the part file is sparse (owner decision, M2), so only the free-space check before the start protects against a full disk.
